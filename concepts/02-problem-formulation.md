# Формулирование проблем

> **One-liner:** Структурированное выделение проблемы из ситуации через 5 элементов описания, формулировку разрыва as-is / to-be, классификацию типа задачи и определение типа корневой причины.

## Слой 1 — Сущность (Знакомство)

Формулирование проблем (проблематизация) — первая фаза цикла системного решения. Превращает размытое «что-то не так» в чёткую формулировку: кто субъект, какой разрыв он испытывает, к какому типу задач это относится и какого рода корневая причина за этим стоит.

Ключевое различение: ситуация объективна (среда, факты, тренды), проблема субъективна (конкретный человек или группа видят разрыв между as-is и to-be). «Нет субъекта — нет проблемы».

**Когда применять:**
- Проблема не сформулирована — есть ощущение «что-то не так», но нет ясности
- Симптом принимают за проблему — команда лечит следствие
- Множество жалоб без структуры — стейкхолдеры описывают разные аспекты одной ситуации
- Начало нового проекта, продуктовой работы, стратегической сессии

**Когда НЕ применять:**
- Задача уже сформулирована и относится к Clear-домену — переход сразу к исполнению
- Нужен детальный анализ причин — это работа следующего этапа (5 Почему, Iceberg, CLD)

## Слой 2 — Концепты-принципы (Понимание)

### Ключевые принципы

| # | Принцип | Формулировка |
|---|---|---|
| 1 | Субъектность проблемы | Без субъекта нет проблемы; ситуация ≠ проблема |
| 2 | Проблема как разрыв | Проблема = gap между as-is и to-be в восприятии субъекта |
| 3 | Две проблемы предпринимателя | Для продукта формулируем проблему пользователя и проблему команды |
| 4 | Тип задачи определяет глубину | Собиратель — исполнение, Охотник — поиск, Координатор — координация |
| 5 | Тип корневой причины определяет инструмент | Простая → действие, убеждения → Iceberg, динамика → CLD |
| 6 | Не подменять проблему решением | Формулировка to-be — про состояние, не про способ |

### 5 элементов описания проблемной ситуации

| # | Элемент | Вопрос |
|---|---|---|
| 1 | Нежелательные явления | Что именно беспокоит? Что хотите изменить? |
| 2 | Почему это важно | Какой ущерб? Какие возможности блокирует? |
| 3 | Контекст | В каких условиях? Какие ограничения? |
| 4 | Стейкхолдеры | Кто вовлечён? На кого влияет? Кто может повлиять? |
| 5 | Желаемая картина будущего | Как выглядит ситуация, когда проблема решена? |

### Правила «если → то»

- Если в описании нет конкретного субъекта, испытывающего разрыв → это ситуация, а не проблема; вернись к шагу определения субъекта
- Если to-be сформулировано через способ («внедрить систему X»), а не через состояние → переформулируй в результат
- Если работаешь над продуктом и сформулирована только проблема пользователя → добавь проблему команды
- Если тип корневой причины — убеждения → следующий инструмент Iceberg Model
- Если тип корневой причины — системная динамика → следующий инструмент CLD
- Если тип задачи Собиратель (Clear) → системный анализ избыточен, переходи к исполнению

### Типизация задачи (три архетипа)

| Архетип | Метафора | Домен | Глубина анализа |
|---|---|---|---|
| **Собиратель** | Собрать ягоды на знакомой поляне | Clear | Минимальная |
| **Охотник** | Поймать оленя — движущаяся мишень | Complicated / Complex | Средняя |
| **Координатор** | Дирижировать оркестром | Complex | Максимальная |

### Типизация корневой причины

| Тип | Характеристика | Дальнейший маршрут |
|---|---|---|
| **Простая / линейная** | Локальная причина, связь очевидна | Действовать сразу |
| **Убеждения / нормы** | Ментальные модели людей, негласные правила | Iceberg Model |
| **Системная динамика** | Петли обратной связи, накопление, задержки | Causal Loop Diagram |

## Слой 3 — Техники (Применение)

### Алгоритм

1. Опиши ситуацию объективно — что происходит, без эмоций
2. Определи субъекта — у кого болит, кто хочет изменений
3. Заполни таблицу 5 элементов (НЯ, важность, контекст, стейкхолдеры, to-be)
4. Сформулируй проблему как gap: as-is → to-be (оба измеримы)
5. Для продуктовой работы — добавь вторую проблему (проблема команды)
6. Классифицируй тип задачи: Собиратель / Охотник / Координатор
7. Применяй 5 Почему — построй 2–3 цепочки от одного симптома
8. Определи тип корневой причины: простая / убеждения / динамика
9. Зафиксируй маршрут к следующему инструменту

### Чек-лист готовности артефакта

- [ ] Субъект проблемы назван явно
- [ ] Таблица 5 элементов заполнена
- [ ] As-is и to-be измеримы
- [ ] To-be описано через состояние, не через способ
- [ ] Для продукта: проблема пользователя и проблема команды
- [ ] Тип задачи определён
- [ ] Построено 2–3 цепочки 5 Почему
- [ ] Тип корневой причины классифицирован
- [ ] Указан следующий шаг (инструмент диагностики)

### AI-промпт

```
Я анализирую проблемную ситуацию.

Вот моё описание:
- Субъект: [КТО]
- Нежелательные явления: [ЧТО]
- Контекст: [ГДЕ, ОГРАНИЧЕНИЯ]
- Стейкхолдеры: [СПИСОК]
- Желаемое состояние: [TO-BE]
- As-is → To-be: [GAP]

Вопросы:
1. Соответствует ли формулировка критерию «разрыв as-is / to-be»? Не подменяю ли проблему решением?
2. Если это продуктовая работа — сформулирована ли проблема команды (не только пользователя)?
3. К какому архетипу относится задача: Собиратель / Охотник / Координатор? Почему?
4. К какому типу относится корневая причина: простая / убеждения / динамика? Какие признаки?
5. Какие альтернативные цепочки «почему» я мог упустить?

Не давай готовых ответов — задавай уточняющие вопросы.
```

## Слой 4 — Кейсы (Рефлексия)

### Кейс 1: Retention мобильного приложения

- **Контекст:** Retention приложения для тайм-менеджмента падает с 40% до 15% за 3 месяца; CAC не окупается.
- **Применение:** Сформулировали 5 элементов. As-is: retention 15%. To-be: retention 30%+ на 3 месяце. Проблема пользователя: приложение не создаёт ощущения прогресса. Проблема команды: нет данных о причинах ухода. Тип задачи — Координатор. Цепочка 5 Почему привела к убеждению команды «удержание = частота открытий». Тип корневой причины — убеждения + динамика.
- **Результат:** Следующий шаг — Iceberg Model по стейкхолдерам. Без формулирования проблемы команды улучшали бы push-уведомления (симптом), а не KPI и метрику успеха.

### Кейс 2: Камеры на онлайн-лекции

- **Контекст:** Преподаватель ведёт онлайн-лекцию, у студентов выключены камеры, он видит чёрные экраны.
- **Применение:** Субъект — преподаватель. As-is: чёрные экраны, не вижу реакции. To-be: вижу лица, веду живой диалог. Тип задачи — Собиратель (известный путь: попросить включить). Тип корневой причины — простая.
- **Результат:** Преподаватель попросил включить камеры; 5 студентов из 20 включили — разрыв частично сократился. Глубокого системного анализа не потребовалось — правильно определили тип задачи.

### Кейс 3: Форсайт в университете (антипаттерн)

- **Контекст:** Преподаватели и студенты обсуждали 2 часа влияние AI на образование, поставили галочку «поработали над стратегией».
- **Применение:** Не выделили субъекта, не сформулировали gap. Обсуждали ситуацию (объективную: AI меняет образование), а не проблему конкретного субъекта.
- **Результат:** Никаких решений и действий. Классический антипаттерн «проблематизация без субъекта». Урок: пока не назван конкретный субъект и его разрыв as-is/to-be, любое обсуждение остаётся разговором о ситуации.

## Слой 5 — Границы, связи, эволюция (Интеграция)

### Границы концепта

- **Где НЕ работает:** в Clear-домене (задача уже понятна, методология избыточна); при глубоком анализе причин (для этого нужны 5 Почему, Iceberg, CLD); как замена стратегическому планированию.
- **Распространённые заблуждения:**
  - Миф: «Проблема — это плохой факт». На самом деле: проблема — это субъективный разрыв, а не объективный факт.
  - Миф: «Сначала найдём решение, потом разберёмся с проблемой». На самом деле: при подмене проблемы решением фиксируется не та цель.
  - Миф: «У продукта одна проблема — пользовательская». На самом деле: для предпринимателя всегда есть две — пользователя и команды.

### Связи с другими концептами

- `cynefin` — дополняет: тип задачи маппируется на домены (Собиратель → Clear, Охотник → Complicated/Complex, Координатор → Complex)
- `five-whys` — следующий шаг: после формулировки строим 2–3 цепочки от симптомов
- `iceberg-model` — следующий шаг при корневой причине типа «убеждения»
- `three-problem-archetypes` — расширяет: детализирует типизацию задачи
- `causal-loop-diagrams` — следующий шаг при корневой причине типа «динамика»

### Антипаттерны применения

- ❌ Описывать ситуацию без субъекта — получается философское обсуждение без точки приложения
- ❌ Формулировать to-be через способ («внедрить CRM») — фиксируется решение, а не результат
- ❌ Брать первую корневую причину из 5 Почему — нужно 2–3 цепочки от одного симптома
- ❌ Игнорировать проблему команды при продуктовой работе — пользователь получит решение, которое команда не сможет доставить
